P-5  source list as map<string, Source>: ordering and duplicates
----------------------------------------------------------------
  REORDERED key order after a wire round trip
            in  ['zeta', 'alpha', 'mu', 'beta']
            out ['zeta', 'mu', 'beta', 'alpha']
            out ['zeta', 'mu', 'beta', 'alpha']
            out ['zeta', 'mu', 'beta', 'alpha']
  UNSTABLE  is the order at least STABLE across PROCESSES?
            5 distinct orderings from 6 separate runs of identical code on identical input: ['alpha,zeta,mu,beta', 'beta,alpha,mu,zeta', 'beta,mu,alpha,zeta', 'beta,zeta,alpha,mu', 'zeta,alpha,mu,beta']. Within one process the order is fixed; across processes the map's hash seed moves, so serializing one corpus today and again tomorrow produces different bytes and a different YAML document.
  UNGUARANTEED what proto3 GUARANTEES about that order
            Nothing. The language spec declares wire ordering and iteration order of map fields undefined. The instability above is that licence being exercised, not a bug.
  UNDETECTABLE two map entries with the SAME key arriving on the wire
            1 entry survives, citation_text='SECOND'; the collision is resolved by the parser, silently, before any validator runs

P-6  CSL citation through google.protobuf.Struct (ERF-8)
--------------------------------------------------------
  LOST      integer fidelity
            in  issued=1494 chapter-number=36
            out issued=1494.0 chapter-number=36.0
  STRUCTURAL why a hand-written CSL message is not the escape
            CSL field names contain hyphens (chapter-number, publisher-place, container-title). A proto identifier cannot. Any typed CSL message needs a rename table the specification does not supply, and CSL-JSON is open-ended, so the table can never be complete.

P-7  unknown fields: what proto3 retention does and does not buy
----------------------------------------------------------------
  PRESERVED an unknown WIRE field survives a proto->proto round trip
            True  (proto3 retains unknown fields since 3.5)
  USELESS-HERE what that is worth for a YAML corpus
            Nothing. A YAML key has a NAME, not a field number. There is no wire field to retain because the value never reached the wire: the reader must decide where to put `granted:` before serializing anything. Preservation requires an explicitly declared map, which is what `unrecognized` is.
