## Verbatim output

1. **[severity: critical] — Canonical serialization cannot represent the normative record model consistently — ERF-53–56; sections 2, 3, 4.2; `Atom`, `Claim`, `Survey` —** ERF-53 requires YAML frontmatter plus a Markdown body “for every record type” and permits multiple records per file, but atoms expressly have no body, while no syntax associates multiple frontmatters and bodies in one file. The atom example is instead a YAML list and omits required self-description. **Smallest fix:** define one canonical envelope per record, ban grouping for v1 unless a complete grouped-file grammar is supplied, and state explicitly that atoms have no body while claims and surveys do.

2. **[severity: major] — Surveys cannot undergo changes that the specification expressly permits — ERF-28, ERF-48; section 3.1 Survey table; `Survey` —** ERF-48 requires every changed record to receive `last_modified`, but `Survey` has no such field. The field table permits corpus transfer, body editing, and adding atoms to `notable_results`, while ERF-28 calls the record immutable. Any such permitted edit is therefore either impossible to stamp or violates immutability. **Smallest fix:** add `last_modified?: ActorStamp` to `Survey` and define only the conducted search acts and reported yield as immutable.

3. **[severity: major] — The specification both ships captures and categorically forbids shipping them — ERF-4, ERF-64, ERF-68; Security and privacy considerations; README; CHANGELOG —** ERF-64 says a corpus travels with records and captures, ERF-68 regulates captures that ship, and the changelog says four licensed captures ship; the security section says captures “MUST NOT be redistributed with a shared or published corpus.” These are mutually exclusive requirements. **Smallest fix:** prohibit redistribution only when the capture’s licence does not permit it, with ERF-5/68 governing the two cases.

4. **[severity: major] — Argument backing traverses edges in directions that do not represent premises — ERF-24, ERF-43; section 5 Relations —** ERF-24 says an argument is checked by granting all claims “its edges name,” and ERF-43 follows both `assumes` and `supports` transitively. But `supports` is defined subject-first: the carrying claim supports the target, so following it from an argument reaches what that argument supports, not a premise it follows from. `conflicts-with` and `decomposes-into` also cannot simply be “granted” as premises. **Smallest fix:** define the exact premise-edge set and traversal direction, most simply making outgoing `assumes` the argument’s premises and treating the other relations separately.

5. **[severity: major] — Survey-backed observations have no defined backing-audit procedure — ERF-24, ERF-25, ERF-49 —** Surveys can make an observation backed and can support a `SUPPORTED as scoped` verdict, yet ERF-24’s observation audit examines only `atoms_for` and `atoms_against`; it never says how cited surveys enter the judgment. Two validators or auditors can therefore treat the same negative claim differently. **Smallest fix:** amend ERF-24 to require examination of `surveys` when the claim relies on absence, sparseness, or coverage.

6. **[severity: major] — Timestamp syntax and ordering are contradictory — section 3 `ActorStamp`; ERF-19, ERF-28, ERF-47, ERF-48, ERF-58; examples —** `ActorStamp.timestamp` is documented as RFC 3339, while the text expressly permits a bare date for `Survey.conducted` and examples use bare dates for `created`. The same type also carries `last_modified`, whose value must be strictly ordered, and audit timestamps used for staleness. No rule defines comparison when one side is a date and the other an instant. **Smallest fix:** require full RFC 3339 instants for `created`, `last_modified`, and audits; give `conducted` a separate type that explicitly permits a full date.

7. **[severity: major] — Required corpus-level artifacts have no normative schema or serialization — ERF-3–5, ERF-59, ERF-64, ERF-68 —** The capture mapping, manifest, and corpus registry are mandatory and validator-visible, but none has a normative data model or file grammar. Capture entries especially lack defined field names and exclusivity rules for path versus absence, note, reason, and licence. This is distinct from the deferred content-hashed capture manifest: even the current mapping cannot be implemented interoperably. **Smallest fix:** add minimal normative interfaces and YAML serialization for these three artifacts without adding hashes or future lifecycle machinery.

8. **[severity: major] — The conformance classes leave mandatory corpus validation outside any appropriate class — section 1 Conformance classes; ERF-3–5, ERF-59, ERF-65–68 —** Corpus conformance is said to bind section 6 plus ERF-62 and ERF-64, excluding the mandatory manifest and capture mapping. Validator conformance binds only section 6, although the conformance suite validates requirements outside it. Thus a “conforming corpus” may omit ERF-59, and a “conforming validator” need not detect that omission. **Smallest fix:** make Corpus bind all corpus-artifact requirements and make Validator bind every machine-checkable MUST applicable to the input it accepts.

9. **[severity: major] — The supposedly deterministic normalization procedure contains undefined parsing operations — ERF-51 —** “Markdown link syntax,” “attribute blobs,” and “parenthesized link targets” have no specified grammar, escaping behavior, or nesting rules. Implementations can legitimately disagree about whether ordinary braces or URL-bearing parentheses are removed, defeating ERF-51’s stated goal that conforming tools reach the same verdict. **Smallest fix:** normatively define these transformations with exact grammar or pseudocode and exhaustive boundary cases; this does not require reopening the declined proposal to outsource normalization.

10. **[severity: major] — Version compatibility rules conflict with Semantic Versioning and with their own rationale — ERF-60, ERF-61 —** ERF-61 requires SemVer but redefines a major change as one making the old corpus “unreadable” rather than semantically incompatible. A field can retain parseable syntax while changing meaning, which ERF-60 itself identifies as the dangerous major-version case. Under the current wording such a change need not increment MAJOR. **Smallest fix:** define MAJOR as any backward-incompatible syntactic or semantic change; reserve MINOR for backward-compatible additions.

11. **[severity: major] — Source-quality anchors assign overlapping sources to conflicting grades — ERF-9, ERF-10 —** `high` includes “an organization’s disclosure about itself,” while `medium` includes “a first party with an interest in the answer” and “a vendor’s claim about its own product.” A vendor disclosure about its own product satisfies both examples, despite the vocabulary being presented as a closed, checkable contract. **Smallest fix:** distinguish accountable regulated/primary records from self-interested promotional assertions, or consistently place first-party self-claims in one tier.

12. **[severity: major] — The normative citation example violates citation completeness — ERF-8; section 4.2 example —** `citation_text` includes Venice and chapter 36, but the supposedly canonical `citation` object contains neither, despite ERF-8 requiring it to carry everything rendered text shows. An implementer copying the primary example produces a nonconforming atom. **Smallest fix:** add the missing publisher/place and locator fields in valid CSL-JSON, then regenerate `citation_text` from that object.

13. **[severity: major] — Audit identities and audit-ledger lifecycle are not coherently specified — section 2 Actor; `AuditEntry`; ERF-11, ERF-40, ERF-48 —** `auditor` is an unconstrained string and examples use names that do not follow the mandatory actor convention, although the prose treats it as an identity. ERF-48 calls audit lists append-only, but only standings receive an enforceable append-only requirement and history check. **Smallest fix:** type `auditor` as `Actor` or define a separate auditor-id grammar, update examples, and explicitly make both audit lists append-only if that is intended.

14. **[severity: major] — Cross-corpus atom resolution is contradicted by the invariant wording — ERF-35, ERF-36, ERF-45 —** ERF-35 says atoms resolve “in their corpora,” which can be read as requiring same-corpus evidence, while ERF-45 expressly permits cross-corpus evidence references in the allowed classification direction. Realm-wide uniqueness makes the narrower lookup unnecessary. **Smallest fix:** state that all record references resolve in the realm namespace, then apply the classification wall independently.

15. **[severity: major] — Narrative-binding identifiers depend on a nonexistent grammar — ERF-31; ERF-13, ERF-28, ERF-36 —** The binding grammar says an id matches “the corpus’s id grammar,” but neither the corpus manifest nor registry declares such a grammar, and claim identifiers have no normative lexical grammar at all. A parser therefore cannot determine conformance from this document alone. **Smallest fix:** define one global record-id grammar, or define binding ids simply as non-whitespace tokens excluding quote/comment delimiters.

16. **[severity: major] — ERF-46 is neither mechanically defined nor consistent with the claim that all invariants are machine-checkable — ERF-18, ERF-46; section 6; conformance coverage —** “The body's opening statement MUST agree” does not define where that statement begins, how headings are skipped, or whether agreement means exact equality or semantic equivalence. Semantic agreement is not mechanically decidable, while section 6 declares every invariant machine-checkable. **Smallest fix:** require a precisely located normalized verbatim restatement, or move the rule back to non-normative authoring guidance.

17. **[severity: minor] — Current README claims about the example corpus are stale — README “Seeing it work”; CHANGELOG 2026-08-23 capture entry —** README says the corpus has five atoms and no captured copy could be republished; the changelog says four licensed captured copies ship while five unavailable-source atoms remain, implying nine atoms and a mixed capture state. **Smallest fix:** regenerate the README counts and capture description from the actual example corpus.

18. **[severity: minor] — ERF-65 attributes YAML 1.1 timestamp behavior to the YAML 1.2 Core schema — ERF-65 —** YAML 1.2 Core does not implicitly resolve date-shaped scalars as timestamps; that behavior comes from YAML 1.1 or implementation-specific legacy schemas. The JSON-schema requirement remains defensible, but its stated interoperability diagnosis is inaccurate. **Smallest fix:** name YAML 1.1/legacy parser behavior rather than the YAML 1.2 Core schema.

## VERDICT

Not ready for v1 beta publication. The core entities are plausible, but the canonical wire format is not presently implementable for all record types, surveys have an impossible modification lifecycle, capture distribution is normatively contradictory, and argument/survey audit semantics are incomplete. Several mandatory corpus artifacts also lack schemas, so independent implementations cannot interoperate from this document alone. Fix findings 1–10 before publication; the remaining major findings should also be resolved because they affect validation outcomes or make supplied examples nonconforming. The stale README and YAML rationale are straightforward cleanup once the normative design is settled.
